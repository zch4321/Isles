# M2：Codex 群聊协作实施计划

> 日期：2026-10-02 · 状态：M2 基线已完成；即时唤醒与主动收信调整见第 11 节
>
> 已确认规则见 [实现计划第 5.1 节](implementation-plan.md#51-本轮已确认规则)。本文记录实现方式、数据与接口边界和验收标准。

## 1. 完成后的使用链路

用户创建多个 Codex Agent，把其中几个拉进群聊并发言。空闲成员立即被唤醒；忙碌成员独立积累未读，原生 turn 结束后立即合并剩余未读开始下一 turn，不等待其他成员结束。Agent 可以在当前 turn 内通过 MCP 主动收信或读取历史，实际返回的消息不再自动投递，自行判断是否回复。用户可以 `@` 某个成员以标明对谁说，可以暂停群讨论，也可以继续与每个 Agent 私聊。每个 Agent 在私聊和所有群中始终使用同一个原生 thread。

拥有拉群权限的 Agent 可以自行建群并邀请已有 Agent；权限默认关闭，由用户在 Agent 详情中开启。

## 2. 范围

本轮包括：

- 产品术语“对象”改为 Agent：界面、文档、数据库、API、MCP 和代码标识同步修改。M1 本地数据不保留，重新生成基线迁移。
- 通用频道模型：私聊与群聊共用频道、成员、消息和按接收者记录的投递。
- 调度：群内发言立即唤醒其他空闲成员，忙碌成员在 turn 结束后合并剩余未读；MCP 收信与历史读取共享接收记录，自动输入超范围未读仍标记跳过。
- 群管理：用户建群、改名、添加和移除成员、暂停与继续；成员变更以系统消息记录在群内。
- MCP：频道内发言与 `@`、历史读取、所在频道与成员、联系人目录；拉群权限下的建群与邀请。
- Web：群聊与 Agent 私聊列表、群聊视图、`@` 选择、成员管理、暂停、权限开关。
- 服务测试、浏览器测试和真实 Codex 冒烟。

不在本轮：Agent 之间私聊、阻塞等待消息工具、讨论预算、产物共享系统、群删除与归档、Agent 改名/换模型/删除、steer、用户登录、Kimi 与 Claude。

## 3. 数据模型

| 表                | 变化                                                                                                                                 |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `agents`          | 由 `objects` 改名；增加 `can_create_groups`，默认关闭。目录为 `<data>/agents/<id>/`。`native_home` 记录其 thread 所在的 Codex 目录。 |
| `channels`        | 增加类型（私聊/群聊）、群名、暂停标记、创建者。私聊仍与一个 Agent 一一对应。                                                         |
| `channel_members` | 新增。频道与 Agent 的成员关系；用户隐含为每个频道的成员。私聊也记录其 Agent 成员。                                                   |
| `messages`        | 发送者类型为用户、Agent 或系统；增加 `mentions`（Agent ID 列表）；去重键包含发送者 ID。                                              |
| `deliveries`      | 主键改为（消息, 接收 Agent）；增加“已跳过”状态；`run_id` 关联实际提交该消息的执行，一次执行可以关联多条投递。                        |
| `runs`            | 不再绑定单条消息，输入由关联的投递记录表示。                                                                                         |
| `events`          | Agent 与频道均可为空，增加频道事件类型。                                                                                             |

投递规则：消息提交时，在同一事务中为频道内除发言者以外的每个成员写入排队中的投递记录。新成员从加入后的消息开始接收投递。移出成员时取消其在该群尚未投递的记录。系统消息（建群、改名、成员变化、暂停与继续）同样投递给成员，使 Agent 知道这些变化，但不触发唤醒。

2026-10-02 增加 `received` 状态，表示消息已被该 Agent 的 MCP 收信或历史读取取出。按消息和接收 Agent 分别记录，不借用“原生执行完成”状态，也不改写已归属原生执行的投递结果。现有 `deliveries.status` 为文本列，无需迁移或清空已有 M2 数据。

## 4. 调度

每个 Agent 仍只有一条执行路径。Runtime 在以下时机重新判断是否启动 turn：新投递、当前 turn 结束、恢复 Agent、继续群讨论、服务启动。移除防抖计时器，执行任务释放时再检查未读，避免遗漏恰好在结束时到达的消息。

- **可唤醒**：Agent 期望运行、状态正常且已有 thread；存在未暂停频道中仍排队的用户或其他 Agent 消息，立即开始 turn。系统消息不单独触发。忙碌时只积累消息，不启动并行 turn，也不等其他成员结束。
- **组装输入**：收集所有未暂停频道的排队投递。每个频道保留最近 10 条与所有 `@` 该 Agent 的未读；私聊中用户消息全部保留。其余标记为已跳过。保留的投递在启动 turn 前标记为提交中并关联执行。
- **信封**：一条 JSON 文本输入，按频道分组，包含频道 ID、类型、名称、跳过条数，以及每条消息的 ID、序号、发送者类型/ID/名称/harness/模型、正文、回复关系、被 `@` 的成员、`mentions_you` 和时间。`turn/start` 的 `clientUserMessageId` 使用执行 ID。
- **终态**：沿用 M1 的接受、完成、中断、失败与待核对规则，作用于该执行关联的全部投递。停止 Agent 时，当前执行关联的投递取消，不再重投。
- **主动收信**：`receive_messages` 按时间取最早未读并按频道返回，可指定频道，默认读取全部成员频道，包括暂停群。默认 50 条、最多 100 条，`has_more` 表示还有未读；无消息时立即返回。只记录实际返回的消息，分页剩余消息不跳过。旧防抖环境变量不再生效。
- **读取去重**：`read_messages` 只标记实际返回的消息，不标记分页探测行或整个频道。暂停期间读过的消息在恢复后也不重复投递；自动唤醒和收信共用持久化接收状态。

权限变更后，服务端校验立即采用新值。若 Agent 空闲则关闭其原生进程，执行中则在当前 turn 结束后关闭；随后立即恢复同一 thread，重新加载 MCP 工具列表。

## 5. 接口

| 操作                   | 入口                                                                          |
| ---------------------- | ----------------------------------------------------------------------------- |
| Agent 列表、创建、详情 | `GET/POST /api/agents`、`GET /api/agents/:id`                                 |
| 修改拉群权限           | `PATCH /api/agents/:id`                                                       |
| 停止、恢复、回答问题   | `POST /api/agents/:id/stop`、`/resume`、`/questions/:questionId/answer`       |
| 频道列表、建群、详情   | `GET/POST /api/channels`、`GET /api/channels/:id`                             |
| 群改名、暂停与继续     | `PATCH /api/channels/:id`                                                     |
| 添加、移除成员         | `POST /api/channels/:id/members`、`DELETE /api/channels/:id/members/:agentId` |
| 读取、发送消息         | `GET/POST /api/channels/:id/messages`                                         |
| 事件                   | `GET /api/events`（SSE 与分页补读，沿用 M1 游标语义）                         |

频道列表携带成员与最后一条消息，Web 不再逐个 Agent 查询预览。频道详情携带最近一页消息和成员尚未回答的原生问题。

## 6. MCP 工具

| 工具               | 可见范围           | 行为                                                                                             |
| ------------------ | ------------------ | ------------------------------------------------------------------------------------------------ |
| `send_message`     | 全部 Agent         | 向自己所在的频道发言；可带 `mentions`（该频道成员）、`replyTo`（同频道消息）、去重标识。         |
| `read_messages`    | 全部 Agent         | 读取所在频道历史，支持 `after`/`before` 分页；实际返回的排队消息记录为已接收。                   |
| `receive_messages` | 全部运行中的 Agent | 在当前 turn 主动收取未读，按频道返回；可限定频道，返回后不再自动投递，分页未返回的消息继续排队。 |
| `list_channels`    | 全部 Agent         | 自己所在的频道、类型、名称、暂停状态与成员。                                                     |
| `list_agents`      | 全部 Agent         | 联系人目录：全部 Agent 的 ID、名称、harness 与模型，不含工作目录。                               |
| `create_group`     | 拉群权限           | 以自己为成员创建群并邀请已有 Agent。                                                             |
| `invite_to_group`  | 拉群权限           | 把已有 Agent 邀请进自己所在的群。                                                                |

发送者始终来自 MCP 连接身份。每次调用重新读取权限与成员关系；隐藏的工具被直接调用时同样拒绝。Agent 已停止时不能发言。

规则说明补充：频道与消息信封含义、`@` 的含义、群内所有发言会被其他成员看到，以及“只有你认为需要回复时，才调用 MCP 发送消息”。

## 7. Web

- 左侧分为“群聊”与“Agents”两组，支持搜索；群聊入口可新建群，Agents 入口可新建 Agent。
- 频道视图统一展示私聊和群聊：发言按发送者分组，系统消息居中显示，`@` 高亮。群聊头部显示成员与运行状态、暂停/继续按钮。
- 群聊输入框输入 `@` 时弹出成员选择，发送时根据正文中的 `@名称` 计算 `mentions`。
- 右侧详情：私聊显示 Agent 配置、会话、拉群权限开关和执行记录；群聊显示成员列表（添加、移除），可进入任一成员的执行详情。
- 群聊中也显示成员尚未回答的原生问题。

## 8. 验收

| 验收项       | 通过依据                                                                                                |
| ------------ | ------------------------------------------------------------------------------------------------------- |
| 工程完整性   | `pnpm check` 与浏览器测试通过。                                                                         |
| 即时唤醒     | 私聊、群聊立即唤醒其他空闲成员；忙时排队，turn 结束后立即处理剩余未读，不等其他成员，不并行执行。       |
| 主动收信     | `receive_messages` 和历史读取只消费实际返回的消息；并发收信、部分读取、分页探测和重启不会重复自动投递。 |
| 合并输入     | 多频道未读只启动一个 turn；每频道最近 10 条加全部 `@` 未读；已投递消息不重复；跳过条数正确且不再出现。  |
| 固定 session | 同一 Agent 在私聊和多个群之间切换、重启后 thread ID 不变。                                              |
| 暂停         | 暂停期间不自动投递但允许主动读取；继续后只投递剩余未读；暂停不中断当前执行。                            |
| 成员与历史   | 新成员可读全部历史；被移出后无法读写，未投递记录取消。                                                  |
| 权限         | 无权限时看不到且不能调用建群/邀请；开启后空闲重启并看到工具；撤销后立即拒绝。                           |
| 发言归属     | 只能向所在频道发言；`mentions` 只能指向该频道成员；原生输出不进入聊天。                                 |
| 真实 Codex   | 两个独立 Agent 在同一群中完成一次讨论，各自经 MCP 发言；thread ID 与私聊一致。                          |

模拟 adapter 用于调度与故障测试；真实 Codex 冒烟使用独立数据目录与少量提示，不能用模拟结果代替。本机 Codex CLI 已从 M1 基线 `0.158.0` 升级到 `0.159.2`，M1 所用协议方法在新版本生成的类型中仍存在。

真实冒烟结果（2026-09-30，`codex-cli 0.159.2`）：用户创建 `sol-1`（gpt-6.1-sol / max）与 `astra-1`（gpt-6-astra / medium），在群“讨论”中发起讨论。两个 Agent 共经 MCP 发言 3 条；`astra-1` 3 次、`sol-1` 2 次执行全部完成，且都使用各自唯一的 thread。本次冒烟未覆盖私聊与重启恢复：两者沿用 M1 的真实验收，以及 M2 服务测试中对同一 thread 与重启的覆盖。

## 9. 后续调整：共用 Codex 目录

2026-09-30 用户决定：Agent 不再使用复制出来的私有 Codex 目录，而是直接共用用户的 Codex 目录（`ISLES_CODEX_HOME`，默认 `~/.codex`）。配置、登录、MCP server、插件、skills、全局 `AGENTS.md` 与长期记忆都共用，只要求每个 Agent 的对话上下文独立。

- **不改用户配置**：Isles 不复制也不写入该目录的配置。每个 Agent 在 `thread/start` / `thread/resume` 的会话级 `config` 中设定自己的 Isles MCP 地址、项目根标记与对 workspace 的信任；审批与沙箱仍按会话传入。
- **MCP 身份**：仍按 Agent 区分地址和 token，以保持按权限显示工具。token 保存在 `<data>/agents/<id>/isles-mcp-token`，经原生进程的环境变量交给 Codex（`bearer_token_env_var`），不进入配置文件和模型上下文。
- **会话位置**：Agent 的 session 保存在共用目录的 `sessions/` 中，可以在 Codex 应用或 `codex resume` 中查看；在其他地方继续对话前应先在 Isles 停止该 Agent。
- **兼容**：此前在私有目录创建的 Agent、或修改 `ISLES_CODEX_HOME` 后的已有 Agent 无法恢复原会话，启动时报错且不创建替代会话，需要重建。

2026-09-30 的真实验证（`codex-cli 0.159.2`，独立数据目录，不影响开发服务）：会话中用户自己的 MCP server 与插件仍然可用；当时 Isles 工具在无权限时为 4 个，开启拉群权限并空闲重启后为 6 个；一次私聊 turn 经 MCP 回复成功；session 写入共用目录；数据目录位于 Isles 仓库内时不加载本仓库的 `AGENTS.md`。首次验证发现 Codex 会在启动 thread 时把 workspace 作为信任项目写入 `config.toml`，加入会话级信任后前后一致。新增 `receive_messages` 后的工具数为 5 / 7。

## 10. 后续调整：不限制原生子代理

2026-09-30 用户明确：harness 自带的子代理是每个 Agent 自己的能力，愿意用就用，Isles 不阻止。此前的实现把“固定 session”理解为禁止子代理，已取消：

- 不再在会话配置中关闭 Codex 的 `multi_agent` / `multi_agent_v2`，沿用用户自己的 Codex 设置；启动规则不再禁止子代理，改为说明主 thread 是该 Agent 在 Isles 的固定身份，子代理经 Isles 工具的发言归属该 Agent。
- 子代理的 turn 事件不结束主 session 的执行；子代理在主 turn 执行期间提出的原生问题可以在 Web 回答，不再被拒绝。
- 执行详情以“子代理调用 / 子代理活动”显示主 thread 中的子代理条目。

## 11. 后续调整：即时唤醒与主动收信

2026-10-02 用户确认：取消私聊和群聊的时间防抖，每个 Agent 独立积累未读；空闲立即启动，原生 turn 结束后立即合并仍未接收的消息。新增 `receive_messages`，现有 `read_messages` 同样记录实际返回的消息，已通过 MCP 接收的内容不再自动启动下一 turn。暂停只限制自动投递，暂停期间主动读到的消息也算已接收。

实现与模块边界：Runtime 移除防抖配置及计时器；Store 共用 `deliveries` 保存 `received`，收信查询与状态变更在一个事务内完成；MCP 校验调用者身份和成员关系，收信立即返回，不提供阻塞等待或全员轮次同步；前端共享协议识别新状态并通过已有 SSE 刷新投递状态。已有 M2 数据和原生 thread 绑定保留。

自动输入仍沿用“每频道最近 10 条加全部未读 @、私聊用户消息全部保留”的规则；本次没有改变自动输入截取范围。主动收信分页不会跳过消息，历史查询只标记实际返回的页。服务测试覆盖即时唤醒、结束时到达的新消息、其他成员仍忙、并发收信、部分历史读取、按接收者隔离、暂停与恢复、持久化、越权和停止约束。

验收结果（2026-10-02）：

- 设置本机 `ISLES_TEST_CODEX_BIN` 后，`pnpm check` 全部通过：格式、ESLint、类型检查、37 项服务测试（含真实 CLI 协议类型生成）与生产构建。
- `ISLES_TEST_BROWSER_CHANNEL=chrome pnpm test:e2e` 的 7 项浏览器测试全部通过，新增用例验证在当前 turn 内通过真实 MCP 接收排队消息，界面消除排队状态且执行记录仍只有一次。
- `pnpm db:generate` 确认表结构没有变化，无需新增迁移；`git diff --check` 通过。
- 真实 Codex 冒烟使用 `codex-cli 0.159.2`、`gpt-6.1-sol / low` 和独立数据目录：Agent 在群内发出就绪标记后排入三条用户消息；它在同一 turn 内用 `receive_messages(limit: 1)` 取第一条、用 `read_messages(limit: 1)` 读第二条，结束后只自动执行剩下的第三条。前两条状态为 `received`、第三条为 `completed`，共两次 completed 执行。停止并重启服务后显式恢复，thread `01a0faa1-191a-7b72-a384-bf8e20e01930` 不变，接收状态保留且没有新增执行。

真实冒烟只使用一个 Agent，多个 Agent 的独立调度与权限由服务测试覆盖。本机脚本与报告保存在忽略目录 `.isles/inbox-acceptance/`，报告为 `data-C3V83P/report.json`；没有操作日常使用的数据目录。
