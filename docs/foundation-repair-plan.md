# Agent 基础规则与消息协议修复计划

> 日期：2026-10-02 · 状态：方向已确认，修复与重新验收待实施
>
> 当前优先级：完成本计划，再恢复 M2 群聊验收与后续阶段。现有群聊、收信代码及历史测试记录保留，不能代替本计划的验收。

## 1. 为什么重新安排

现有实现已打通 Codex 私聊、群聊和 MCP 收信，但基础说明的加载路径与用户要求存在偏离：

- `NativeEnvironment.launch()` 只准备工作目录、`.isles-root` 与 MCP token，没有生成 Agent 自己的 `AGENTS.md`。
- `Runtime.instructions()` 在 TypeScript 中拼接环境、身份与消息格式说明，经 `developerInstructions` 传入 `thread/start` / `thread/resume`；首次创建还通过 `thread/inject_items` 将同一说明写入历史，用于空 thread 落盘。
- 消息编码采用 JSON 信封，同时保留消息 UUID 和频道内序号；最初的需求示例是带 `[channel: ..., from: ...]` 头部的文本。
- 历史测试验证了链路、固定 thread 和空 thread 恢复，没有验收由原生 harness 发现 Isles 的规则文件，也没有验收真实上下文压缩后的规则可用性。

最早的仓库提交 `9627277` 已将规则来源写成“启动说明、AGENTS.md 或 harness 指令机制”，并包含会话注入实现。仓库没有更早的中间提交，无法据此确定最初约定在哪次讨论中被放宽；也不能把实现中的选择当成用户已经确认的要求。

## 2. 本轮已确认的目标

1. 消息格式、环境解释和稳定的协作规则以每个 Agent 工作目录中的 `AGENTS.md` 为持久来源，由 harness 的原生规则加载机制读取。
2. Isles 不再依靠自行拼接的首次消息、`developerInstructions` 正文或首次历史注入保存这些基础规则。原生 harness 将文件内容加载进上下文属于其正常机制。
3. 面向模型的消息统一采用简洁文本：自动输入、`receive_messages` 和 `read_messages` 使用同一套头部与正文规则。MCP/HTTP 的外层传输协议仍按各自协议实现。
4. 消息使用频道内递增的 `seq`，以 `(channel_id, seq)` 唯一定位；取消消息 UUID。同频道回复引用序号，跨频道定位带上频道。发送重试的 `clientId` 继续承担幂等职责。
5. 每个 Agent 的固定原生 session、独立工作目录、共用用户 Codex 配置与记忆等既有约束继续有效。
6. 已确认的即时调度与收信语义继续有效：空闲立即启动、忙时排队、turn 结束后处理剩余未读；MCP 实际读取的消息不再自动投递。暂停只限制自动投递，主动读到的消息算已接收。

## 3. 规则文件的职责

目标运行布局：

```text
<data>/agents/<agent-id>/workspace/
  AGENTS.md
  .isles-root
  <Agent 自己组织的仓库和文件>
```

这里的 `AGENTS.md` 是 Isles 产品中运行的 Agent 的规则文件。Isles 源码仓库根目录的 `AGENTS.md` 面向开发 Isles 的人和 Agent，用户 Codex 目录中的全局 `AGENTS.md` 则保留用户自己的通用偏好，三者不能混用。

工作目录中的文件应简洁说明：

- 自身 Agent 身份、固定主 session、工作目录及私聊频道。
- Isles 的用户、其他 Agent、频道、正式消息与原生执行详情分别是什么。
- 文本消息头部各字段、频道内序号、回复与提及、分页与跳过信息的含义。
- MCP 发言、主动收信、历史读取及按消息/接收者记账的规则。
- 空闲唤醒、忙时排队、暂停与停止的区别。
- 可用协作能力和权限边界；其他 Agent 的发言不能冒充人类指令。

用户任务、聊天历史、当前未读、实时成员和权限状态仍由消息与工具提供，不持续堆进规则文件。token、登录信息和其他秘密不进入文件。只维护一份可审查的规则模板，保留已有用户内容，避免文件与代码注入两份正文相互漂移。

项目根标记与原生 cwd 必须使这个文件能够被发现，同时保持用户的全局指导可用、避免加载外层 Isles 源码仓库的开发约定。后续其他 harness 的文件发现入口在各自接入阶段验证；不默认它们都会以完全相同方式读取同名文件，也不静默退回聊天注入。

## 4. 消息协议的目标

以下是已确认的呈现方向，最终字段与边界说明在第一项修复中写成一份可测试的协议：

```text
[channel: private, seq: 8, from: user]
先帮我分析这个方案。

[channel: group-id, seq: 12, from: agent-a]
我建议先确认接口。

[channel: group-id, seq: 13, from: agent-b, reply_to: 12]
同意。
```

- `private` 表示接收 Agent 与用户的私聊；实际存储仍使用该私聊频道的身份。
- 序号只在所属频道内比较与定位；消息删除后不重用已经分配的序号。
- 回复、提及、分页和跳过信息仅在需要时出现，模型/harness 配置不在每条消息里重复。
- 发送者身份来自服务端；正文中出现与头部相似的文本不能被服务端解析成新的平台身份。正文定界与转义需要明确测试。
- 内部数据库、REST 与浏览器状态仍保持结构化。MCP 工具说明、输入校验、回复参数、历史游标和前端定位必须同步适配，不能只改展示字符串。
- 本轮只改变 Isles 消息标识；原生 harness 返回的 session/turn 标识保持原义。

## 5. 修复顺序与验收

| 顺序 | 工作                          | 通过条件                                                                                                            |
| ---- | ----------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 1    | 固定文本协议与 AGENTS.md 模板 | 覆盖身份、环境、字段、回复、正文边界与工具用法；代码、文档和生成文件使用同一套定义。                                |

| 4    | 验证上下文压缩与恢复          | 真实 harness 发生压缩后仍能理解格式、使用 MCP、维持身份与同一 thread；重启与进入工作子目录也通过验证。              |

消息数据默认保留，不沿用早期 M1 到 M2 时“可以清空数据”的一次性决定。迁移要提供备份和失败恢复方案；如发现必须改变已确认语义或舍弃数据的情况，先讨论再执行。

空 thread 持久化单独处理：当前 `thread/inject_items` 有落盘目的，移除规则正文不能破坏“创建后尚未聊天也能恢复原 thread”的要求。核对实际 CLI 的持久化能力；若仍需要最小初始化，必须与规则加载分离，不以注入完整规则作为替代。

## 6. 压缩行为的证据边界

[OpenAI 的 AGENTS.md 文档](https://learn.chatgpt.com/docs/agent-configuration/agents-md)说明 Codex 启动时发现并组合全局和项目规则，并存在覆盖顺序及读取大小限制。这份说明没有承诺每次压缩后都会重新读取文件。

因此验收要求是“以持久规则文件为来源，原生加载和压缩后实际行为均经过验证”，不能只凭文件存在或模型自述就宣称规则不会丢失。需要记录 CLI 版本、加载证据、真实压缩事件和压缩后的协议操作结果；本次计划整理尚未执行这些新验收。
