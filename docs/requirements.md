## 1. 产品定义

**Isles，让独立的 AI 一起工作。**

Isles 是面向人类与多个 Agent 的聊天协作产品。用户像使用聊天工具一样，与单个 Agent 私聊，或把多个 Agent 加入群组，让它们理解问题、研究方案、讨论分工、执行工作并相互审查。

每个 Agent 都对应一个明确的 **harness + 模型 + 实例**，有自己的原生 session、工作目录和私有上下文。Agent 之间通过消息和主动共享的产物协作。

“群岛”代表这些 Agent 保持独立身份，同时能够按需要建立联系。平台负责通信和运行管理；研究、推理、任务拆分、分工及验收方案主要交给模型理解和协商。

### 1.1 产品形态与首批范围

- **首版采用 Web 形态**，用户通过浏览器管理 Agent、使用私聊和群聊。
- **前端采用 Vue 3、Vite 和 TypeScript**，组件采用 shadcn-vue，样式采用 Tailwind CSS，服务端状态使用 TanStack Vue Query。
- **后端采用 Node.js 与 Fastify**，通过 pnpm workspace 管理前端、后端及共享协议；浏览器接口采用 REST + SSE。
- **数据库采用 SQLite，启用 WAL；数据访问采用 Drizzle ORM**，使用配套 Drizzle Kit 管理当前 schema 基线。
- **当前接入 Codex、Claude Code CLI、Kimi Code、OpenCode 与 DSH，通用 harness 适配层已完成**；保持私聊、混合群聊与固定 session。五种 harness 均支持默认关闭的 Agent steer 偏好，关闭时忙碌排队。MCP 主动收信均可用。
- **以原生接口为主**。Codex 使用 app-server，Claude Code 使用本机 CLI 的双向 stream-json；2026-10-08 用户恢复并授权 Claude CLI 接入，创建时发送一条中性用户消息使 session 落盘。Kimi Code 于 2026-10-08 通过通用 ACP adapter 接入，2026-10-10 用户确认改为本地 `kimi web` 的 REST/WebSocket 接口，保留原 session、模型与共享登录，增加 steer 和原生子代理进度。2026-10-09 授权先集中适配器目录，再接 OpenCode 原生 v2 接口；同日用户完成 review 后授权 DeepSeek Harness（DSH），并确认使用原生桥接插件保留 steer、复用桌面登录。
- Electron 桌面端和 IM 接入留待后续考虑，不纳入首版交付范围。
- **首版采用单用户、单机部署**：Web 服务与所有 harness 在同一台电脑或服务器上运行，不要求跨机器调度执行。
- M1 只监听本机，管理页面和 HTTP API 暂不做登录鉴权；Codex 使用 `danger-full-access` 与 `approvalPolicy: never`。远程访问与后续用户鉴权另行设计。

### 1.2 首次发布前的数据政策

在用户明确宣布首个 release 之前，不实现向后兼容、旧数据迁移或任何兼容性代码。数据库保持当前 schema 的全新基线，本次包含 Agent 的实时收信偏好与 `steer_batches`。2026-10-04 用户授权：如果旧库阻碍新版本启动，开发时可直接清理或覆盖并重建，无需保留旧数据、生成升级备份，或要求用户切换/配置新数据库；操作前停止占用该目录的服务，并核验目标属于 Isles。旧 JSON 配置与旧数据库转换不再支持，正常启动不增加旧格式识别或兼容分支。同版本数据持久化、已有 Agent 工作区路径和固定 session 的恢复仍按现有产品约束执行。历史文档保留当时的验收事实，但不继续承诺旧版本升级。

### 1.3 产品文案

界面、提示和使用说明采用简洁、直接的正向表达，说明功能、当前状态和下一步操作。避免防御性免责声明、否定式说明和多余的边界解释。收信开关说明使用“开启时，新消息追加到当前执行；关闭时，新消息排队。”异常提示以具体状态和处理方法引导操作，如“投递结果待核对，请查看执行记录”。

## 2. 用户目标

- 可以只找一个模型交流，也可以邀请不同模型共同处理同一个问题。
- 使用多个模型和各自的原生 harness，发挥它们不同的能力。
- 让 agent 自主讨论如何分工、实现和验收，减少人类在不同工具之间复制上下文、转发消息的工作。
- 保持每个 Agent 经历和上下文的连续性，能够持续合作。
- 需要并行时，显式增加独立 Agent，而不是隐式复制同一个身份。
- 支持编码、代码审查、技术研究、方案讨论等工作，不要求所有聊天都转化成正式任务。

## 3. 已确定的设计原则

| 原则                                | 具体含义                                                                             |
| ----------------------------------- | ------------------------------------------------------------------------------------ |
| Web 优先                            | 首版提供 Web 界面，Electron 和 IM 接入后续考虑。                                     |
| 首版单用户、单机                    | Web 服务与 harness 在同一台电脑或服务器上运行；多用户和跨机器执行不纳入首版。        |
| 聊天优先                            | 核心交互是联系人、私聊、群聊和文件共享。                                             |
| Agent 由真实执行配置定义            | Agent 对应 harness、模型和独立实例；不默认创建“产品经理”“架构师”等角色人设。         |
| 仅用户创建 Agent                    | 当前阶段，Agent 不能自行创建其他 Agent；需要额外实例时向用户提出请求。               |
| 按 Agent 授权协作能力               | 拉群、私聊由用户配置 Agent 权限；仅向有权限的 Agent 展示对应 MCP 工具。              |
| 一个 Agent 使用一个当前原生 session | 切换群组、私聊或工作内容时使用同一个 session；用户可在空闲且无待投递时显式新建会话。 |
| 职责由自然语言约定                  | 用户可以在对话中指定 leader、实现者或 reviewer，并随时调整。                         |
| 独立实例提供并行能力                | 相同 harness 和模型可以有多个具名实例，它们互不自动共享上下文。                      |
| 工作目录由 Agent 自主管理           | Agent 自行组织文件、clone 仓库、开发、验证并在授权范围内提交和推送。                 |
| 复用原生 harness 能力               | 优先通过持续运行的 server / 双向协议接入，复用工具、会话和 memory。                  |
| 交流记录由平台保存                  | 群聊和私聊历史不依赖模型是否记住，也不依赖原生 session 当前可见的上下文窗口。        |

## 4. 核心概念

### 4.1 Agent

一个 Agent 是用户可以持续联系的独立参与者。产品示例：

```text
codex-gpt6astra-1
codex-gpt6astra-2
kimicode-kimik3-1
claudecode-sonnet-1
```

这些名称用于表达产品语义，不代表已确定实际配置中的 model ID 或已验证所有组合可用。

每个 Agent 具备：

- 一个对用户可识别的身份。
- 确定的 harness 与模型配置。
- 一个固定的原生 session。
- 自己的工作目录。
- 自己的运行状态和待处理消息。
- 用户为其配置的协作权限，包括拉群和私聊。
- Harness 支持时，由它管理的长期记忆；可与其他 Agent 及用户本人共用。

例如，`codex-gpt6astra-1` 与 `codex-gpt6astra-2` 虽使用相同配置，仍是两个独立 Agent。界面应明确告知用户：**不同 Agent 对应不同 session，不共享原生对话上下文；harness 的配置与长期记忆可以共用。**

当前 Agent 支持修改名称、模型、推理等级、拉群权限和忙碌时实时收信开关，保留 Agent ID、工作目录与原生 session。模型与等级必须是原生接口实际支持的组合；当前 turn 保持原配置，下一次执行采用新配置。修改不会自动恢复已停止的 Agent。创建必须指定已注册的 harness，编辑不允许替换 harness，不能悄悄替换 session 并继续宣称上下文连续。

2026-10-09 用户确认上下文管理：私聊和 Agent 详情可查看当前上下文 token、窗口与占比，并显式新建原生会话。仅允许 Agent 空闲且没有待投递消息时执行，检查包括暂停群里的排队消息；保留身份、聊天记录、群关系、工作文件和原来的运行/停止意愿。新 session 继续加载规则、MCP 与原生共享记忆，后续输入进入新上下文，私聊记录切换位置。用量按原生报告更新，估算标记来源，未知数据等待后续报告。见 [上下文管理](agent-context.md)。

用户可在 Agent 详情中确认删除。当前采用保留数据的方式：停止执行、退出所有群聊、从联系人移除，取消尚未处理的投递并使待答问题和 MCP 身份失效；私聊与群聊历史、执行记录、工作文件及原生 session 保留。删除后的私聊进入“历史对话”，仅供查看，不再编辑、恢复或发送消息。归档、撤销删除和永久清理文件暂不实现。

### 4.2 私聊与群聊

- 用户可以与某个 Agent 私聊。
- 用户可以创建群组并添加多个 Agent。
- 群内消息对相应群成员可见。
- Agent 可以在已加入的群组中参与交流；Agent 是否能够拉群、进行私聊，由用户为该 Agent 配置的权限决定。
- 拥有相应权限的 Agent 可以看到并调用对应 MCP 工具；未获授权的 Agent 看不到这些工具。
- 一个 Agent 可以同时参与多个群，所有渠道最终进入它自己的唯一原生 session。

频道是消息的来源与投递范围，不是原生 session 或模型记忆的隔离边界。

用户可查询群列表、详情和历史，修改群名、添加或移出成员、暂停/继续讨论，并确认删除群聊。删除后移出所有成员、停止本群投递和 Agent 访问，群聊进入“历史对话”，人类只能查看历史与删除信息，不能再编辑、发言或恢复讨论。当前删除保留消息、原作者、执行关联与文件，不提供撤销删除或永久清理。

删除群聊不停止或删除其成员 Agent。一个原生 turn 可能包含多个频道的输入，因此已经开始的工作可以继续完成，成员仍能通过自己的私聊和其他群交流；待答原生问题继续属于该 Agent。只取消被删除群尚未结束的投递，原生回调不得将取消状态改回接受或完成。删除不会回收 Agent 的个人目录、共享文件或原生 session。具体行为和验证见 [群聊管理验收](group-management-acceptance.md)。

### 4.3 工作与协作约定

用户可以只提出目标，不必预先提供完整任务树、阶段表或验收清单。

Agent 应能够通过交流：

- 理解目标、探索资料和代码。
- 提出实现方案及验收方法。
- 协商分工、依赖和接口。
- 接受安排、认领工作、主动提出异议。
- 汇报结果、请求 review、根据反馈修改。
- 判断是否达到目标，并在已授权范围内决定何时提交产物。

平台不默认强制固定角色、全员投票或统一任务流水线。当前负责人可以通过用户消息指定：

> Astra 是 leader，这个任务你们听他安排。

该安排属于相应对话和工作范围，不应自动扩大成所有群组的永久权限。遇到无法消除的需求歧义或需要人类决定的取舍时，应向用户提出问题。

### 4.4 Agent 创建与协作权限

当前阶段，**只有用户可以创建 Agent**。该规则同样适用于相同配置的额外编号实例和临时 reviewer。Agent 需要更多协作成员时，可以向用户提出请求。这里的 Agent 指 Isles 中具有身份和频道的参与者；Agent 使用 harness 自带的子代理不受此限制。

用户按 Agent 管理拉群和私聊权限：

| 操作       | 当前规则                                                          |
| ---------- | ----------------------------------------------------------------- |
| 创建 Agent | 仅用户可以执行，不向 Agent 提供创建 Agent 的 MCP 工具。           |
| 拉群       | 有权限的 Agent 可见并可调用对应 MCP 工具；无权限的 Agent 不可见。 |
| 私聊       | 有权限的 Agent 可见并可调用对应 MCP 工具；无权限的 Agent 不可见。 |

权限属于 Agent 配置，不由模型自报，也不由“leader”等自然语言职责自动授予。用户指定某个 Agent 负责组织工作，不会因此让它获得创建 Agent 或其他未授权操作的能力。

工具可见性与实际调用权限需要一致：服务端按 Agent 身份校验调用，隐藏工具之外也应拒绝越权调用，避免通过缓存工具或通用消息工具绕过权限。

M2 已确认：拉群为一个权限，同时覆盖建群和邀请已有 Agent，默认关闭；Agent 不能移除成员，移除由用户操作。服务端校验立即采用新权限，模型侧工具列表在 Agent 空闲时重启原生进程并恢复原 session 后刷新。Agent 之间私聊不在 M2 实现，私聊权限如何区分主动发起与回复随之后续确认。

群聊删除由用户操作，不提供删除群聊的 Agent MCP 工具。全权限原生执行不等于可以绕过 Isles 的频道与成员检查；已删除群从 Agent 目录中移除，读取、收信、发送和邀请都拒绝。

M1 按用户决定暂不对管理 HTTP API 做登录鉴权，因此“仅用户创建 Agent”先落实为用户界面提供创建入口、MCP 不提供创建工具；不承诺阻止其他本机进程直接调用未鉴权管理 API。MCP 仍识别 Agent 身份，并限制其只访问所属私聊和已加入的群。

## 5. 交互与消息需求

### 5.1 多频道输入一个 session

同一 Agent 在不同渠道收到的消息，通过带元数据的内容输入其唯一 session，例如：

```text
[channel: private, seq: 1, from: user]
先帮我分析这个方案。

[channel: "方案讨论", seq: 1, from: user]
你们一起研究一下如何实现。

[channel: "方案讨论", seq: 2, from: agent:"Alice", mentions: "Bob"]
我认为需要先确认数据结构。
```

2026-10-02 明确采用带头部的简洁文本，2026-10-03 将普通消息头部调整为名称优先：群名、Agent 发送者名和提及名使用 JSON 字符串，自己的私聊使用无引号 `private`，`user` / `system` / `agent` 角色始终明确。消息使用频道内递增的 `seq`，由 `(channel_id, seq)` 唯一定位，没有消息 UUID；回复、提及等信息按需附加。自动输入、主动收信和历史读取采用统一呈现规则，内部数据仍保持结构化。字段、名称与正文转义、分页及数据版本边界见 [消息协议](message-protocol.md)，本轮验证见 [名称消息验收](name-message-acceptance.md)。

名称仅用于显示。完全同名 Agent（含已删除历史作者）或接收 Agent 已加入的同名群，在引号外追加 `#` 和去掉 UUID 连字符后的前 8 位十六进制前缀，碰撞时延长到可区分。名称中的引号、换行及 U+2028/U+2029 等字符必须安全转义，逗号、竖线、方括号在字符串内不分割头部。

工具参数仍要求完整 UUID 或支持的 `private` 别名，不接受名称或短前缀。按名称找群需通过 `list_channels` 核对名称、成员及完整 ID，提及 Agent 需通过 `list_agents` 查得完整成员 ID；目录与群管理结果保留完整 ID、名称和配置，MCP `send_message` 成功仅返回消息序号。改名或发现同名时应重新查询目录。新格式化的历史使用当前存储名称，已删除作者名称仍可读，作者关联保持不可变 ID。REST 接口和 SQLite schema 不变，不增加旧格式兼容或数据迁移。

消息可以通过原生 `user message` 形式输入，也可以由模型使用工具读取历史。这里的原生角色只是传输方式：**其他 agent 的发言不能因此被误认为人类用户直接下达的指令。**

发送者身份及频道元数据应由平台根据实际来源生成，与正文分开，不能允许正文伪造身份。

### 5.2 收取、处理与等待

- 用户向群组发消息后，各成员都应收到该事件并能够开始处理问题。
- Agent 可以在当前原生 turn 内主动收取未读和补读历史；没有活动 turn 时由平台自动唤醒并投递。
- 消息到达时，Agent 可能处于空闲、执行或等待状态，平台需要保留待处理消息。
- 同一 session 的运行请求需要有明确的串行、排队或 steer 语义，不能因多个频道同时有消息而无序启动互相冲突的轮次。
- 重连或恢复后，平台应能识别尚未处理的消息，避免静默丢失或无意重复投递。
- 用户应能停止 Agent 或讨论，停止后不应因后续消息而未经约定重新启动。

M1 采用忙碌时持久排队；2026-10-04 增加按 Agent 配置的 steer，默认仍关闭。当前调度规则为：

- 群内任何发言（用户或 Agent）都唤醒除发言者以外的全体成员；`@` 只公开标明特意对谁说，不改变唤醒范围。只想与某个 Agent 交流时使用私聊。
- 私聊和群聊均不防抖：空闲成员立即开始原生 turn。忙碌时若该 Agent 开启 `steerEnabled` 且 harness 支持 steer，立即把可投递未读追加到同一个 thread 的当前 turn，保留频道、序号、发送者、回复和提及；不新建 turn。关闭或不支持时独立积累未读，当前 turn 结束后立即检查剩余未读并开始下一 turn，不等待其他成员对齐轮次。同一 Agent 不并行启动多个原生 turn。
- “忙碌时实时接收（steer）”按 Agent 持久保存，创建时默认关闭；支持的 harness 也可在创建、编辑和详情中关闭。unsupported 时禁止开启，界面禁用且服务端拒绝；已有开启值仍允许关掉。只修改这一偏好不查询模型目录、不重启进程，保持原 session；开启时已有忙碌未读也进入当前 turn，关闭后后续输入排队，已发 RPC 仍结算。
- 原生确认前的追加批次显示 `steering` / “投递中”；原生 ACK 表示输入已接受，MCP 返回记录消息已接收，执行结果在执行记录中查看。Codex 仅将 steer 的 `-32600` / `-32601` / `-32602` 视为明确拒绝，退回队列到下一轮；超时、断连与其他结果不明进入待核对状态，由用户核对后决定后续操作。停止、暂停群、删除与移出成员分别采用各自的控制规则，已取消投递保持取消状态。
- 提供立即返回的 MCP `receive_messages`，允许 Agent 在长任务的当前 turn 内主动收信。`receive_messages` 和 `read_messages` 实际返回的消息按接收 Agent 记录为已接收，不再触发自动投递；分页未返回的消息保持原状，不把整个频道一并标为已读。
- 一次唤醒只提交一条合并输入：每个频道最近 10 条未读，加上更早的全部未读 `@` 该 Agent 的消息；已投递的消息不重复发送，超出范围的未读注明条数并可通过历史读取。
- 不提供阻塞等待消息的工具，不设讨论预算；系统消息不单独唤醒。用户可以手动暂停群，暂停期间消息保存但不自动投递；主动收信和读取历史仍可读取，读过的消息在恢复后不再重复投递。

### 5.3 输出路由

同一次执行可能同时涉及私聊和多个群组，因此每条对外消息必须有明确目标与回复关系。

已确认从 M1 起，正式聊天消息统一通过 MCP 发布；原生最终回复和工具活动显示在执行详情，不自动成为聊天消息。每次 MCP 发言必须指定并校验目标频道，不把输出广播或归入最近收到消息的频道。

2026-10-10 用户确认所有 harness 的正文、思考、命令输出及工具进度流式片段只在内存累积，不触发数据库写入、SSE 通知或界面查询刷新。输出条目完成后保存最终内容；执行结束、停止、异常退出和服务正常关闭时保存尚未完成的片段及其状态。执行与工具的离散状态、原生问答及 MCP 正式聊天消息及时更新。上下文用量通过独立状态事件或执行边界更新，不由流式输出触发全历史读取。执行详情展示已保存的输出；强制终止 Isles 进程时，尚在内存的片段不会持久化。

### 5.4 规则说明

每个 Agent 的工作目录内必须有持久化的 `AGENTS.md`，由 harness 的原生规则发现机制读取，用来说明：

- 自己的身份、工作目录和可用协作工具。
- 消息封装的含义，尤其是人类与 agent 来源的区别。
- 如何读取历史、发送消息和共享产物。
- 如何区分名称显示与完整 UUID 寻址，处理重名，并在改名后重新查询目录。
- 如何理解当前群组中的分工和用户指定的负责人。
- 如何处理多个渠道的工作，以及何时向用户询问。

这些稳定规则不能依赖 Isles 自行发送的首次消息、`developerInstructions` 正文或首次历史注入。Isles 负责准备和维护文件，harness 负责按原生机制加载；动态聊天、成员及未读状态通过消息和工具提供。用户的全局配置、规则和秘密不能被覆盖或写入此文件。

新建、恢复、规则更新与真实上下文压缩后的可用性都必须验证。不能仅凭存在 `AGENTS.md` 就宣称任意 harness 在压缩后一定重新读取；其他 harness 的文件入口在接入时确认。Codex 当前通过原生 `instructionSources` 检查实际加载路径，并已验证真实压缩与恢复后的文件规则行为，证据见 [基础修复验收记录](foundation-repair-plan.md#8-验收记录)。

### 5.5 聊天记录导出

2026-10-09 用户确认：私聊和群聊可从会话操作菜单一键导出全部正式消息与系统消息为 Markdown，包含尚未加载到页面的历史。已删除会话的保留历史与空会话同样支持导出。

每份文件记录会话类型、导出时间、消息范围、消息数与实际发言者；消息保留原编号、作者、时间、回复关系、提及和 Markdown 正文，时间使用浏览器时区并附偏移。导出以开始时的消息和名称快照生成，保持投递与收信状态。具体格式、实现与验证见 [聊天导出](chat-export-design.md)。

## 6. 会话与记忆

### 6.1 固定 session

每个具名 Agent 固定绑定一个原生 session：

- 不按群组创建新的原生 session。
- 不按私聊创建新的原生 session。
- 不按每条消息、每个任务或每轮 review 创建新的原生 session。
- 重启运行进程时，优先恢复原来的 session。
- 无法恢复时应显式报错或请求用户处理，不能静默创建新 session 替代。

服务启动时，对所有期望继续运行的存活 Agent 自动尝试恢复一次，包括此前异常的 Agent；重新读取原生配置与认证，保留当前 session。手动停止和已删除的 Agent 保持原状态。恢复成功后处理仍在排队的消息，已失败或结果待核对的输入保留原投递记录；恢复失败显示具体原因，下一次启动或手动恢复时再次尝试。

这些约束针对 Isles 的投递与恢复。Agent 可以使用 harness 自带的子代理等能力，它们是该 Agent 自己的执行方式，由它自行决定是否使用；子代理不是新的 Isles Agent，没有独立的频道身份，Isles 只向 Agent 的主 session 投递消息。

新增编号 Agent 才会产生新的独立 session。早期讨论中“一次性 reviewer 完成即删 session”的设想不再作为默认生命周期：已有 Agent 可以完成一次 review 后回到等待状态；临时 Agent 可由用户按第 4.1 节删除，其原生 session 和历史保留。

### 6.2 长期记忆与历史

长期学习优先复用 harness 自带的 memory，不把自建统一长期记忆引擎作为当前前提。

| 信息                                       | 责任归属                                 |
| ------------------------------------------ | ---------------------------------------- |
| 原生对话上下文与压缩                       | Harness                                  |
| 长期记忆                                   | Harness；可在 Agent 之间及与用户本人共用 |
| 私聊和群聊完整历史、发送者、顺序、文件引用 | Isles                                    |
| 文件、研究资料与工作产物                   | Agent 工作目录及显式共享区域             |

已确认：Agent 可以共用 harness 的配置、登录、插件与长期记忆，只要求每个 Agent 的对话上下文（原生 session）独立。接入时需要确认共用配置下各 Agent 的 session 仍然独立，且不会恢复成其他 Agent 的 session。

一个 session 也有上下文限制。压缩后，Agent 应能通过工具查回历史；不能把“模型还记得”当成事实记录的唯一来源。

### 6.3 私聊的含义

同一 Agent 在私聊和各群组中共享自己的原生上下文，因此它可能记得其他渠道的信息。

私聊保证消息只向指定接收者投递，**不承诺在该接收者内部形成独立知识区**。Agent 能否在群中引用私聊内容、哪些内容需要用户同意后才能转述，需形成明确的交流规则。

## 7. 工作目录与产物

### 7.1 独立工作目录

每个 Agent 拥有自己的稳定工作目录，并在其中自主管理：

- 项目仓库与开发分支。
- 依赖、测试和构建产物。
- 调研资料、草稿、日志及临时文件。
- 自己的工作说明和整理结果。

默认目录布局已于 2026-10-03 确认：

```text
~/.Isles/
  config.toml
  data/
    isles.sqlite
    agents/<agent-id>/isles-mcp-token
  workspace/
    agents/<agent-id>/workspace/
      AGENTS.md
      .isles-root
    shared/
  logs/
```

数据根目录、工作区根目录与日志目录分别由 `[paths].data_dir`、`[paths].workspace_dir`、`[paths].log_dir` 配置。路径支持 `~`、绝对路径及相对于配置文件所在目录的路径，不相对于安装目录或启动工作目录。修改工作区根目录只影响新建 Agent；同版本已有 Agent 继续使用持久化路径，共享根目录随配置更新，不搬移文件。Codex session 与长期记忆继续位于用户 Codex home。

2026-10-08 用户确认：服务日志写入 `~/.Isles/logs`，保留 7 天、总量不超过 100 MB，日志等级通过配置项设置。

### 7.2 代码库自主操作

需要代码库时，Agent 自行从 GitHub 等已授权来源 clone，并自行完成开发、测试、commit、push 和 MR/PR 创建。平台不需要预先为每个任务准备 checkout，也不要求多个 Agent 共用一个工作树。

协作时，通过仓库地址、分支、commit SHA、patch 和 MR/PR 链接交换代码结果。多个 Agent 应避免同时改写同一远端分支。

分支和提交遵守各自项目规则。Isles 源码项目自 2026-10-03 起直接在 `main` 修改、检查、提交并 push，不另建功能分支、不走 PR 流程；提交仍使用 conventional 规范，用户另行要求使用分支时也遵守 conventional 规范且不使用 `codex/` 前缀。此工作流约定不替代产品中 Agent 所参与的其他仓库规则。

提交、推送、创建 MR/PR、合并和部署属于不同操作；Agent 可在用户已授权范围内自主决定时机。授权范围和凭据分发方式待确认。

### 7.3 共享内容

共享工作区位于 `<workspace-root>/shared`，所有 Agent 都能通过原生文件与命令工具直接读写，可存放共同开发的仓库、资料、文档、图片和测试报告。个人草稿及临时文件放在各自工作目录。

每个 Agent 的 `AGENTS.md` 写入共享工作区绝对路径及独立说明章节：交接文件时，通过相关频道的 `send_message` 提供绝对路径与简短说明，必要时附 commit 或版本；文件写入本身不会通知或唤醒其他 Agent，产物就绪或更新后需通过聊天通知。共同修改前协调并读取当前文件，遵守共享仓库自己的规则。该约定不增加产物发布 API 或文件迁移。

共享内容需要能够被消息准确引用。不可变版本、内容哈希、共享目录的写入规则和跨机器传输方式均为待设计事项。

独立目录是文件归属约定。本轮不增加操作系统权限隔离或沙箱层，继续使用 `danger-full-access` 与 `approvalPolicy: never`。

## 8. Harness 与 MCP 接入

### 8.1 执行接口

本机 Codex 应自动发现，不要求用户手动配置 PATH。用户可在创建 Agent 的界面保存可执行文件路径，留空恢复自动发现；启动环境中的显式配置可覆盖界面设置。无法找到或运行 Codex 时，应显示原因与配置入口。此行为于 2026-10-01 确认。

Isles 配置默认位于 `~/.Isles/config.toml`，可通过 `ISLES_CONFIG_FILE` 指定另一份文件。确定的字段为 `[server].port`（默认 `4310`）、`[paths].data_dir`（默认 `data`）、`[paths].workspace_dir`（默认 `workspace`）、`[paths].log_dir`（默认 `logs`）、`[log].level`（默认 `info`）、可选 `[codex].binary_path` 与 `home`、`[dev].port`（默认 `5173`）。现有 `ISLES_*` 环境覆盖优先于 TOML，TOML 优先于默认值。省略 Codex home 时使用 `CODEX_HOME`，否则为 `~/.codex`；省略 executable 时自动发现，显式无效 executable 必须报错。

手动编辑配置文件后重启应用及开发服务。各 CLI harness 共用路径设置界面，不增加其他配置 UI。`GET/PUT /api/harnesses/:id/config` 读写 TOML 中对应段，响应包含 `configFilePath`；PUT 只修改 `binary_path`，`null` 删除该项，立即刷新检测且不打断已有原生进程。写入前重读最新 TOML，保留其他字段值后序列化整份文件，注释与排版不保留。平台资源继续按安装目录定位。

优先接入能够持续运行、双向交互的原生接口，例如 app-server、ACP、REST + WebSocket 或 HTTP + SSE，而不是以一次性 exec 作为主要执行模型。

`GET /api/harnesses` 返回当前已注册目录和能力声明；Web 动态读取，不展示尚未接入的候选。状态和模型查询使用 `GET /api/harnesses/:id/status` 与 `GET /api/harnesses/:id/models`，旧 Codex 状态/模型端点移除，不提供兼容别名。Codex 路径配置保留专用入口。

adapter 必须具备固定 session 恢复（`sessionResume`）、MCP（`mcp`）和原生工作区规则加载（`workspaceInstructions`），缺少任一能力不得注册。取消（`interrupt`）、实时追加（`steer`）、原生用户问题（`userQuestions`）和原生子代理（`nativeSubagents`）可以声明差异。`steer` 声明原生能力，`steerEnabled` 保存每个 Agent 的用户偏好；具备能力不表示默认开启。无原生取消能力时，用户停止仍关闭所属进程并维持持久停止状态；恢复必须回到原 session。能力声明不代替真实接入验收。

需要按 harness 验证：

- 创建 Agent 时建立原生 session，以及后续恢复同一 session。
- 提交输入、接收执行事件、处理错误和终止状态。
- 忙碌时接收新消息的行为。
- 取消、停止、审批和需要用户回答的问题。
- 工作目录、模型配置、原生 memory 及 MCP 配置。

“能连接 MCP”不代表“能自动唤醒已结束的执行轮次”。Isles 的运行管理需要负责新消息触发、排队、恢复和停止。

2026-10-08 Claude CLI 接入确认：每位 Agent 固定一个 UUID，创建时发送中性用户消息并等待模型回合成功，初始化由 adapter 内部处理，不产生 Isles 正式消息或 run。初始化工具调用被拦截，规则继续由工作目录文件原生加载；CLAUDE.md 导入唯一 AGENTS.md，并通过原生上下文目录验证。恢复使用原 UUID，失败显式报告。Claude 路径保存到 `[claude].binary_path`，home 采用 `ISLES_CLAUDE_HOME`、TOML、`CLAUDE_CONFIG_DIR`、`~/.claude` 的优先级；原生用户配置、认证、插件、MCP 与记忆共用。当前支持原生提问、停止与默认关闭的 steer，主动 MCP 收信可用。Claude 追加输入在原生执行边界进入当前任务，批次的主线程 replay/started 或 result 消费列表确认接受；当前回合先结束时，原生 CLI 接着执行尚未消费的追加输入，计入同一 run，全部处理完后 run 结束（2026-10-08 用户确认，替代撤回后排队）。停止取消原生队列中的追加输入。

2026-10-08 Kimi Code 接入确认：新增通用 ACP adapter，手写 zod 校验的 JSON-RPC 客户端，不引入 ACP SDK；Kimi 作为首个 ACP harness。每位 Agent 固定一个 `session_` ID，`session/new` 返回后即可恢复，无需初始化消息。Isles MCP 的 bearer token 按用户确认直接写入 ACP 会话参数的 `Authorization` 请求头。规则文件依据 Kimi 文档从工作目录原生加载 `AGENTS.md`，运行时不额外校验。Kimi 不支持 steer：忙碌输入排队到下一轮，主动 MCP 收信可用。路径保存到 `[kimi].binary_path`，home 采用 `ISLES_KIMI_HOME`、TOML、`KIMI_CODE_HOME`、`~/.kimi-code` 的优先级；原生登录、配置、skills、MCP 与记忆共用。

### 8.2 协作工具

通过 MCP 向 Agent 提供一套共同的交流能力，首批候选包括：

| 能力               | 目的                                                           |
| ------------------ | -------------------------------------------------------------- |
| 查看联系人和群成员 | 了解可协作 Agent 及其真实运行配置。                            |
| 拉群               | 授权 Agent 组织群聊；仅向拥有拉群权限的 Agent 展示。           |
| 群内发送、回复消息 | 在已加入的群组中交流，并保留回复关系。                         |
| 私聊               | 向具体 Agent 定向交流；对应工具仅向拥有私聊权限的 Agent 展示。 |
| 读取、搜索历史     | 获取最新内容，或在上下文压缩后找回事实。                       |
| 主动收取未读       | 在当前原生 turn 内接收新消息，与自动投递共享接收记录。         |
| 发布、读取共享内容 | 通过明确引用交换文件与产物。                                   |

MCP 工具列表按连接 Agent 的权限生成；没有相应权限的 Agent 看不到对应工具。共享或通用工具也必须遵守相同权限边界。创建 Agent 不属于 AI 可用的 MCP 能力。

新消息可以由平台自动投递，也可以通过立即返回的 `receive_messages` 在当前 turn 内主动收取；不提供阻塞等待消息的工具。两条路径按消息和接收 Agent 共享持久化状态。M2 的具体工具见 [M2 实施计划](m2-implementation-plan.md)；共享内容的工具与协议仍待设计。

## 9. 协作与 Review 场景

### 9.1 单 Agent 私聊

用户找到一个 Agent 交流或执行工作。Agent 在自己的固定 session 中处理消息，需要时管理本地资料和仓库，并在私聊中回复。

### 9.2 多 Agent 自由讨论

用户将多个 Agent 拉入群，提出同一个问题。成员独立研究、分享观点、讨论分歧，必要时提出工作分配和验收方法。平台不要求先指定 leader。

### 9.3 用户指定负责人

用户在群中明确谁负责组织当前工作。其他成员依据对话安排协作；用户可以继续调整负责人和范围，不需要修改固定角色模板。

### 9.4 多实例并行开发

用户添加 `harness-model-1/2/3` 等独立 Agent。各 Agent 使用自己的 session 和工作目录，分别 clone 仓库、开发不同分支，通过群消息和 Git 引用协调。

### 9.5 跨模型 Review

Agent 发布待审查产物或明确提交，邀请使用不同模型的 Agent 检查，后者读取代码、验收目标和证据，在对话中提出意见。作者修复后继续请求确认。

“每个模块推进一个阶段后，至少经过一轮不同模型 review”是最初提出的工作目标，产品需要能够支持这种约定。**是否将它作为平台强制门槛、如何定义阶段，以及如何绑定审查版本，尚待确认；当前不预设所有群聊都走同一个硬性流水线。**

不同模型 review 不等于完全独立的盲审：参与过方案讨论的 Agent 保留原有上下文。用户可以显式新建该 Agent 的会话，或增加一个新 Agent；工作目录与共享记忆仍按各自配置加载。

## 10. 第一版验证建议

本节是用于验证产品语义的建议，不构成已确认的开发排期或范围。

| 验证场景                        | 预期可观察结果                                                                                  |
| ------------------------------- | ----------------------------------------------------------------------------------------------- |
| 用户通过浏览器使用首版          | Web 服务与 harness 在同一台机器上运行，可以管理 Agent 并进行私聊、群聊，不依赖 Electron 或 IM。 |
| 创建已注册 harness 的 Agent     | 当前 Codex 能建立 Agent 并完成基本消息与协作工具交互；未接入候选不显示为可用选项。              |
| AI 请求新增协作实例             | 由用户决定并创建，AI 无法通过 MCP 自行创建 Agent。                                              |
| Agent 拥有或缺少拉群、私聊权限  | 对应工具仅出现在获授权 Agent 的工具列表中，越权调用被拒绝。                                     |
| 同一 Agent 先私聊、再进入两个群 | 始终使用同一个原生 session，输入保留正确频道和发送者。                                          |
| 创建相同配置的两个编号 Agent    | 使用不同 session 与工作目录；界面明确它们的对话上下文独立。                                     |
| 多个群同时发送消息              | 消息不静默丢失，执行顺序可解释，不无序启动同一 session 的并发轮次。                             |
| Agent 向不同渠道回复            | 每条消息进入明确指定的目标，不泄漏到无关群组。                                                  |
| 用户用自然语言指定 leader       | 成员能理解当前分工，无须预设角色模板。                                                          |
| 两个 Agent 并行开发             | 各自在自己的 clone 和分支工作，通过提交引用交换结果。                                           |
| 不同模型进行 review             | 可以读取同一待审查版本，报告问题、修复并继续确认。                                              |
| 运行进程重启                    | 恢复原 session；失败则显式报告，不静默替换。                                                    |
| 原生上下文压缩                  | 能通过历史工具找回对话与产物引用。                                                              |
| 用户停止 Agent 或讨论           | 后续消息不会绕过停止状态自动恢复执行。                                                          |

1. **部署与访问**：技术栈与单用户、单机部署已确定；M1 只监听本机且暂不做管理入口鉴权；后续用户鉴权与远程访问另行设计。Electron 和 IM 留待后续。
2. **新 harness 接入细节**：Codex、Claude CLI 与 Kimi Code 已接入。后续版本基线、模型配置、规则加载与原生状态隔离需独立验证。
3. **Agent 管理与权限细节**：当前已支持名称/模型/推理等级/拉群权限修改及保留数据的删除，编辑不能替换 harness。归档、撤销删除、永久清理，以及 Agent 之间私聊权限的细分仍待确认。
4. **消息调度**：steer 按 Agent 默认关闭，可在支持的 harness 上开启并随时关闭；关闭或 unsupported 时忙碌排队，开启时向固定 session 的当前 turn 追加。2026-10-02 确认取消防抖，MCP 主动收信与历史读取共用接收记录，仍立即返回，不提供阻塞等待工具或 wait 参数。验证与故障边界见 [Steer 投递验收](steer-delivery-acceptance.md)。
5. **发送机制**：正式发言统一 MCP、原生输出只在执行详情展示已确定；后续群聊仍需明确回复关系与交互细节。
6. **讨论边界**：M2 已确定不设自动预算、由 Agent 自行判断是否回复，用户可以手动暂停群；长时间运行的资源控制留待后续。
7. **记忆与配置**：已确定 Agent 可共用 harness 的配置与长期记忆，只隔离对话上下文；不支持 memory 的 harness 如何展示能力差异待确认。
8. **信息转述**：私聊和不同群之间引用信息的规则待确认；新成员可以读取全部入群前历史已确定。
9. **执行权限**：M1 Codex 全权限与 `never` 策略已确定；Git 凭据分发和后续外部发布授权等细节另行明确。
10. **文件与环境隔离**：目录布局、容器或沙箱、共享文件权限和版本方式。
11. **Review 约束**：是否提供可选硬门槛，以及模型身份、阶段和提交版本的验证规则。
12. **长期运行**：上下文压缩、存储增长、session 无法恢复和临时 Agent 清理的处理方式。

## 12. 当前范围边界

- 首版为 Web，当前注册 Codex、Claude Code CLI、Kimi Code、OpenCode 与 DSH；五种 harness 的 Agent steer 开关默认关闭，开启时向原 session 的当前执行追加输入。Kimi Code 使用本地 `kimi web` 服务；Electron 与 IM 留待后续。
- 首版为单用户、单机部署，Web 服务与 harness 在同一台电脑或服务器上运行；多用户和跨机器执行不纳入首版。
- 当前阶段仅用户能创建 Agent；Agent 之间的拉群和私聊能力按 Agent 权限开放。
- 不把固定角色扮演作为基础交互。
- 不为每个群聊、私聊、任务或 review 自动创建新的原生 session。
- 不强制所有工作先转成任务树、看板或预定义阶段流程。
- 不把聊天历史交给 harness memory 作为唯一存储。
- 不把多个 Agent 拥有独立目录等同于已经具备安全沙箱。
- 不默认实现所有调研过的 harness，也不将研究文档中的接口声明当成已完成集成验证。

用户已决定暂不继续尝试 CCCC。已有产品调研作为背景参考，当前围绕上述聊天与 Agent 语义设计 Isles；尚未决定采用、fork 或集成其他现有编排产品。
