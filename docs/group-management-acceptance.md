# 群聊基础管理验收

日期：2026-10-03。补齐群聊增删改查，复用既有创建、改名、成员管理与暂停/继续界面，新增删除确认和只读历史，保持现有前端风格。

## 1. 行为与边界

- 用户可以创建群、查询列表/详情/历史、修改名称、添加或移出成员、暂停/继续和删除群。
- 删除确认明确说明：群聊转入“历史对话”、成员退出、本群消息投递与 Agent 访问结束；历史、执行关联、个人目录和共享文件保留。取消按钮默认聚焦。
- 删除后人类仍可查看群历史和创建/删除时间；没有输入框、改名、成员操作或暂停/继续。其他窗口删除正在查看的群时，页面自动转为只读，成员执行检查器返回群详情。
- 群聊删除不停止或删除成员、不关闭原生进程、不改变原生 session 或待答问题；已经开始的原生 turn 可能继续完成，私聊和其他群仍可用。只取消被删除群的 `queued` / `skipped` / `submitting` / `accepted` 投递，其他终态保留。
- 原生接受/完成回调只更新仍处于提交中或已接受的投递，避免较晚回调把已删除群的取消状态覆盖为完成。一个共享 turn 中的其他频道可以继续完成。
- 默认频道列表和 Agent 目录不再列出该群，调度和主动收信排除该群；MCP 读取、收信、发送与邀请都拒绝。重复删除幂等；当前不提供恢复群或永久清理历史/文件。

管理 HTTP API 仍只监听本机且未做用户登录鉴权。这里的“用户操作”指 Web/管理入口；全权限执行不提供 Agent 间操作系统隔离，MCP 继续校验身份、频道和成员关系。

## 2. 数据与接口

频道 DTO 增加 `deletedAt: string | null`。删除状态由 SQLite `events` 表中的永久 `group_deleted` 标记及其创建时间派生，不新增 SQL 列，不改变当前 schema 基线，不转换任何旧数据。此事件承担持久业务状态，后续普通事件回放历史清理必须保留删除标记。

删除事务保存最后一条系统通知、暂停状态、成员退出、取消投递和删除标记，事务提交后才向订阅者通知；标记保存失败则全部回滚。频道、消息、序号、原作者、run 输入与原生详情保留，文件和 session 不清理。

| 接口                                                      | 行为                                                                        |
| --------------------------------------------------------- | --------------------------------------------------------------------------- |
| `GET /api/channels`                                       | 默认排除已删除群；`includeDeleted=true` 包含历史群。                        |
| `GET /api/channels/:id`、`GET /api/channels/:id/messages` | 人类仍可读取已删除详情和历史。                                              |
| `PATCH /api/channels/:id`                                 | 名称/暂停状态部分更新，空/未知字段拒绝；已删除返回 `410`。                  |
| `DELETE /api/channels/:id`                                | 返回已删除频道；重复调用保持相同状态，私聊返回 `400`。                      |
| 成员管理                                                  | 已删除群拒绝添加和移出成员（`410`）。                                       |
| `POST /api/channels/:id/messages`                         | 已删除群拒绝写入（`409`），相同 clientId 的重试也不能绕过。                 |
| Agent MCP                                                 | 已删除群返回工具错误；不提供删除群的 MCP 工具，自己的私聊与其他群继续可用。 |

## 6. 阶段判断

在单用户、本机、Codex 范围，配置、独立与共享工作区、Agent/群聊管理、消息、权限、固定 session、停止/恢复和持久规则已有闭环证据，可以按计划进入 M3。先核对 Kimi 安装版本并提取 adapter 边界，复用既有业务与消息模型；Kimi 的规则加载、固定 session、MCP、交互、停止/恢复和与 Codex 的混合群聊需独立验收，再进入 M4 Claude Agent SDK。

M5 的检索、文件版本与预览、一致性备份和更长时间运行仍需后续完善，不阻塞开始 M3。本轮没有接入 Kimi/Claude，也不将 Codex 验证扩展成它们已经可用的声明。
